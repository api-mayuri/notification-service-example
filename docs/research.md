# Исследование: что берём, что делаем иначе и почему

Интернет был доступен только через веб-поиск и чтение страниц. Maven Central, Docker Hub и GitHub API из среды разработки закрыты, поэтому:

- README примера прочитан через веб-страницу репозитория;
- `DESIGN.md` и код в `app/` недоступны, выводы о них сделаны по README;
- справочная информация о Spring и Kafka сверена с актуальной документацией точечно (Resilience Features, Modulith API, Retry Topics). Остальное — по знаниям на середину 2026 года, помечено в `docs/progress.md`.

## Пример-ориентир: Fred123-dev/Notification-Service (Python, FastAPI)

Как устроен:

- `Notification` разворачивается в записи `NotificationDelivery` по каналам.
- Задачи кладутся в `asyncio.PriorityQueue` в памяти процесса, пул асинхронных воркеров шлёт в провайдеры-заглушки с синтетическими сбоями.
- Есть повторы с экспоненциальным backoff и circuit breaker на канал.
- Идемпотентность по `(user_id, idempotency_key)`.
- `POST /notifications/batch` до 500 элементов с ответом 207.
- Предпочтения (opt-in/opt-out по каналам), вебхуки о статусе, статистика `/analytics/stats`.
- Шаблоны в памяти, аутентификации нет, контакты пользователя «делегированы внешнему сервису». Развёртывание — одна реплика из-за очереди в памяти.

## Что берём

| Идея | Где у нас |
|---|---|
| Разбиение уведомления на доставки по каналам | Агрегаты `Notification` и `Delivery` |
| Идемпотентность по ключу | Пара `(client_id, key)`, уникальный индекс, отпечаток тела, 422 при повторе с другим телом |
| Пакет до 500 с ответом 207 | `POST /api/v1/notifications/batch`, каждый элемент в своей транзакции |
| Предпочтения | `RecipientPreferences`: отписки по каналам и категориям, тихие часы, пояс, язык |
| Экспоненциальный backoff | `RetryPolicy` (с jitter) + retry-топики Kafka |
| Circuit breaker на канал | Resilience4j, декоратор `ResilientChannelSender` |
| Статистика | `GET /api/v1/statistics` по каналам, статусам и периодам (HOUR, DAY) |
| Уведомления о статусе | События в `notification.events.v1` через outbox вместо «выстрелил и забыл» |

## Что делаем иначе и почему

| В примере | Проблема | У нас |
|---|---|---|
| Очередь в памяти | Одна реплика, потеря при перезапуске | Kafka + transactional outbox (Spring Modulith); состояние в PostgreSQL |
| Шаблоны в коде | Нельзя менять без релиза, нет локалей и версий | Шаблоны в БД: версии, активная версия, локали с fallback, предпросмотр, Thymeleaf |
| Контакты только у внешнего сервиса | Некуда слать без интеграции | Контакты в запросе + порт `RecipientResolver` (HTTP-клиент по желанию) |
| Провайдеры-заглушки | Ничего не доставляет | SMTP и webhook — рабочие; SMS, Telegram, WhatsApp, push — порты и логирующие заглушки с флагом `simulated`, чтобы не путать с реальной доставкой |
| Нет аутентификации | Любой шлёт уведомления | OAuth2 Resource Server, scopes, отправитель видит только свои данные |
| Самописный circuit breaker, плоская структура | Дублирует готовое, сложно расширять | Луковая архитектура на модулях Maven, Resilience4j, `@Retryable`/`@ConcurrencyLimit` из Spring 7 |
| Вебхуки о статусе в отдельном механизме | Событие теряется при сбое | Outbox → Kafka; подписчики читают `notification.events.v1` |

## Архитектурные источники

- **Эванс и Вернон.** Агрегаты маленькие; между агрегатами — eventual consistency через доменные события (ADR 0006). Value objects проверяют себя в конструкторе.
- **Палермо, Onion Architecture.** Зависимости внутрь, инфраструктура на краю (ADR 0002).
- **Richardson, microservices.io.**
  - *Transactional Outbox* — Modulith Event Publication Registry.
  - *Idempotent Consumer* — уникальные ключи, статусная машина, оптимистическая блокировка.
  - *Polling Publisher* — повторная отправка незавершённых публикаций по расписанию.

## Стандарты

- **CloudEvents 1.0, Kafka binding (binary mode):** атрибуты `ce_*` в заголовках.
- **AsyncAPI 3.0:** `docs/asyncapi.yaml`.
- **RFC 9457:** Problem Details с `errorCode`.
- **IETF draft Idempotency-Key:** 400 без ключа, 422 при повторе с другим телом, 409 при параллельной обработке, `Idempotent-Replayed` при повторе.
- **RFC 9110:** 202 + Location, 409, 422, 429 + Retry-After.
- **E.164 и RFC 5322 (упрощённый addr-spec):** проверка телефона и email.
- **BCP 47 и IANA TZ:** локали и часовые пояса.
