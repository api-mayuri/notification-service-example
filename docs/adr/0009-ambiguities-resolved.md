# ADR 0009. Как разрешены неоднозначности промпта

- **Статус:** принято. Ответы на вопросы из разбора промпта; заказчик согласился собирать сервис с рекомендованными решениями.

| Вопрос | Решение |
|---|---|
| Заглушки возвращают успех, статус `SENT` вводит в заблуждение | `SendResult.Success` несёт флаг `simulated`. Он хранится в доставке, виден в API (`deliveries[].simulated`), событиях и метриках (`outcome=simulated`) |
| Статус `DELIVERED` недостижим без callback'ов провайдеров | Переход `SENT → DELIVERED` реализован в домене (`Delivery.confirmDelivered`, событие `DeliveryConfirmed`). Эндпоинт приёма подтверждений не входит в объём: у каждого провайдера свой формат, это следующий шаг вместе с реальными провайдерами |
| Idempotency-Key «для всех POST» | Обязателен для `POST /notifications` и `/notifications/batch`. Отмена идемпотентна по смыслу, повторная отмена возвращает 200. Шаблоны и предпросмотр — управляющие операции без ключа. В Kafka `client_id = ce_source`, ключ — `idempotencyKey` из данных или `ce_id` |
| Категория SYSTEM | Ведёт себя как TRANSACTIONAL: не отключается отпиской, игнорирует тихие часы. Отписаться можно только от MARKETING |
| `PENDING → SKIPPED (тихие часы с отменой)` противоречит «MARKETING откладывается» | Тихие часы **откладывают** отправку (`nextAttemptAt` = конец тихих часов в поясе получателя). `SKIPPED` — только отписка или нет контакта |
| Превышение лимита частоты | Доставка откладывается (ADR 0008) |
| RecipientResolver: нет контракта сервиса пользователей | По умолчанию `RequestOnlyRecipientResolver` — контакты только из запроса. `HttpRecipientResolver` включается `RECIPIENT_DIRECTORY_URL`, контракт в его JavaDoc. Сервис пользователей вызывается, только если в запросе нет нужного контакта |
| Нет контакта для канала | Доставка `SKIPPED` с причиной `NO_CONTACT`. Если контакта нет ни для одного канала — `422 NO_DELIVERABLE_CHANNEL` |
| Очистка ключей идемпотентности | Задача планировщика освобождает ключи старше `notification.delivery.idempotency-key-retention` (по умолчанию 7 дней, не меньше 24 часов). Сами уведомления не удаляются |
| 207 Multi-Status из WebDAV (RFC 4918), а не RFC 9110 | Оставлен: это устоявшийся способ вернуть результат по каждому элементу пакета. В теле у каждого элемента HTTP-код, который он получил бы при отдельной отправке |
| Каждое изменение статуса доставки — событием | Публикуются все переходы, кроме технического `SENDING`: `delivery.scheduled`, `sent`, `retry-scheduled`, `failed`, `skipped`, `cancelled`, `delivered` и `notification.accepted/completed/cancelled` |
| Кто видит уведомление | Только отправитель (`client_id`). Чужое уведомление — `404` |
| `ChannelType` — enum или открытый тип | Открытый value object (`record ChannelType(String code)`) с константами известных каналов. Новый канал не требует правки домена. То же для `ContactType` и `ChannelAddress` |
