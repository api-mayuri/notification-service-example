# ADR 0008. Ограничение частоты

- **Статус:** принято

## Лимит запросов клиента (429)

Используется Resilience4j `RateLimiter` (конфигурация `clients`), отдельный лимитер на каждого клиента. Фильтр `ClientRateLimitFilter` стоит после аутентификации и при превышении отвечает `429 Too Many Requests` с `Retry-After`.

**Ограничение:** лимит считается в памяти экземпляра, поэтому при N экземплярах общий лимит равен N × limit. Для точного распределённого лимита нужен общий счётчик (Redis + Bucket4j). Это зависимость вне стека, отложено как следующий шаг.

## Лимит частоты на получателя и канал

Промпт не определял, что делать при превышении. Решение: **откладывать** доставку, а не отклонять и не пропускать.

- Лимиты задаются в `notification.delivery.rate-limits.<канал>` (`max`, `window`, `categories`).
- По умолчанию лимит действует только на MARKETING, чтобы не задерживать сброс пароля.
- Воркер перед отправкой считает отправленные в окне доставки по БД (`sent_at`). Если лимит исчерпан, доставка остаётся `PENDING`/`RETRY_SCHEDULED` с `nextAttemptAt` = момент освобождения окна, а планировщик поставит её позже. Попытка не расходуется.
- Счёт по БД работает при любом числе экземпляров. Индекс — `ix_delivery_rate`.
